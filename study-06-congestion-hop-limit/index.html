Hop limits that know how busy the node is

Three static ceilings decide how far a packet travels, and none of them knows whether the repeater applying them has any airtime left. Taking one hop off each ceiling when the budget runs low is one comparison. On this network the budget never ran low, so nothing happened.

Where it comes from

allowPacketForward() enforces flood_max, flood_max_unscoped and flood_max_advert. All three are compared against the packet's hop count alone. The node's own transmit budget, tracked a few hundred lines away in the dispatcher, is not consulted.

The change

A repeater nearly out of airtime is the likely bottleneck, and packets that have already travelled a long way are the least likely to reach anybody new. Below a quarter of the window's allowance, reduce each ceiling by one hop.

uint8_t squeeze = isBudgetLow() ? 1 : 0;
if (packet->getPathHashCount() + squeeze >= _prefs.flood_max) return false;

Cost. One comparison per forwarding decision, and a budget query that the dispatcher already maintains.

What was predicted, before running it

Reach shrinks slightly; congestion collapse under load is avoided. Pre-registered as best measured on the large network, which is the one used here.

What happened

The condition never fired

Identical to three other arms in this series. `isBudgetLow()` compares the remaining budget against a quarter of the window, and with average airtime near two per cent the budget never fell that far, so the ceilings were never reduced.

Why it came out that way

The change is conditional, and its condition depends on the same transmit budget that idea 05 raises. On this workload that budget stays comfortably full: 527 seconds of airtime shared across 308 transmitting nodes over ninety seconds.

So this arm ran the modified binary, verified by checksum, and executed the unmodified path every time. It is not evidence that the idea is wrong; it is evidence that the test could not reach it.

Testing it needs offered load rather than a single flood: many senders, sustained, until repeaters begin deferring transmissions. That is a different scenario from the one this series used, and building it is the prerequisite for judging this idea at all.

Should it be adopted?

Undecided, and not testable yet

No decision either way. The mechanism is cheap and the reasoning is sound, but nothing here exercised it. The useful next step is not to adjust the idea but to build a congested scenario, at which point this arm and idea 08 both become measurable.

For

  • Costs one comparison, using state the dispatcher already keeps.
  • Targets the right packets: far hops carry the least new reach per transmission.
  • Degrades gracefully rather than dropping traffic outright.

Against

  • Untested: its condition did not occur once in this series.
  • Reduces reach exactly when the network is busiest, which is when reach matters most.
  • A quarter of the window is an arbitrary threshold with no evidence behind it yet.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
