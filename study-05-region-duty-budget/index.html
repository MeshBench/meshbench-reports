A duty budget the band would recognise

Every MeshCore repeater ships willing to transmit for half of every hour. EU 868 sub-bands commonly allow one or ten per cent. Setting the default to the legal figure for the band these nodes sit in changed nothing measurable, because the network never came close to either ceiling.

Where it comes from

_prefs.airtime_factor ships at 1.0, and getAirtimeBudgetFactor() turns that into 1/(1+1): a fifty per cent duty cycle, on every repeater, by default. The dispatcher tracks a transmit budget against it and defers when the budget runs low.

Fifty per cent is five times the allowance for 869.4 to 869.65 MHz and fifty times the allowance for the 1% sub-bands.

The change

Set the shipped default to 9.0, which is 1/(1+9), or ten per cent. The default is changed rather than the accessor, so an operator can still set it with set af.

_prefs.airtime_factor = 9.0;   // was 1.0, which is a 50% duty cycle

Cost. None at runtime.

What was predicted, before running it

Delivery falls and airtime falls sharply. The stated purpose of the arm was not to find an improvement but to measure what the shipped default costs in compliance terms.

What happened

No measurable change, and that is the finding

The numbers are indistinguishable from three other arms in this series. Measured airtime was about 1.7 seconds per node over ninety seconds, roughly two per cent, so neither a fifty per cent ceiling nor a ten per cent one was ever reached.

Why it came out that way

A duty cycle limit is a ceiling, not a target. It changes behaviour only when a node is busy enough to hit it, and on this network no node came close: total airtime across 308 transmitting nodes was 527 seconds over a ninety second run, which averages under two per cent per node.

That makes this arm a measurement of the workload rather than of the change. A flood test with four originators does not saturate a repeater. Sustained traffic from many senders would, and that is the scenario in which this change matters.

The compliance point stands independently of the result. The shipped default permits five times the airtime the band allows for these frequencies. Nothing in this run needed that headroom, which is precisely why lowering it costs nothing here.

This arm returned the same five numbers as ideas 03, 06 and 07. Each ran a different binary, confirmed by checksum in every run record, so this is four changes converging on one outcome rather than one binary run four times. What they share is that none of them altered relaying behaviour on this workload.

Should it be adopted?

Yes, but not on this evidence

The change is almost certainly right, and this run is not the argument for it. A default that permits five times the legal airtime is a defect whether or not a given network reaches it, and the correct evidence is a regulatory citation rather than a flood test. Adopt it on those grounds, and measure its cost separately on a saturated network.

For

  • Brings the shipped default within the limit for the band these radios use.
  • No runtime cost: it is one constant.
  • Costs nothing measurable on a network of this load, so the change is safe to make.
  • Leaves the operator's own setting working, because the default rather than the accessor is changed.

Against

  • Unmeasured where it matters. Its effect appears only under sustained load, which this workload does not produce.
  • A single value cannot be right everywhere: 869.4 to 869.65 MHz allows ten per cent, other EU 868 sub-bands allow one, and the correct figure depends on the frequency in use.
  • Lowering a ceiling can only reduce delivery under load; how much is not established here.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
