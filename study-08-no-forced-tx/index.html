Not forcing a transmit through a busy channel

When listen-before-talk has reported the channel busy for too long, MeshCore transmits anyway on the theory that the radio may be stuck. On a busy mesh the channel is not stuck, it is busy. Removing the forced transmit cost nothing in delivery and bought a measurable reduction in collisions.

Where it comes from

Dispatcher::checkSend() tracks how long the channel has been reported busy. Past getCADFailMaxDuration() it sets ERR_EVENT_CAD_TIMEOUT and falls through to the transmit, on the assumption that a radio reporting busy for that long is misbehaving.

That assumption is right on a quiet band with a faulty radio, and wrong on a busy mesh where the channel genuinely is occupied.

The change

Back off and retry instead of transmitting. The error flag is still raised, so a genuinely stuck radio remains visible in diagnostics.

_err_flags |= ERR_EVENT_CAD_TIMEOUT;
cad_busy_start = 0;
next_tx_time = futureMillis(getCADFailRetryDelay());
return;                        // upstream falls through and transmits here

Cost. None.

What was predicted, before running it

Fewer collisions under congestion, and no effect at all when the channel is not contended.

What happened

Distinct, and in the right direction

Collisions fell 4.0% and transmissions 3.5%, with reach down 3.9 points and airtime up 13.9%. The only arm besides ideas 01 and 02 to produce numbers of its own, and the only one whose condition actually occurred.

Why it came out that way

Unlike ideas 05, 06 and 07, this arm's code path was reached: the channel on a 311 node network with four simultaneous originators does report busy for long stretches, which is exactly the condition upstream treats as a stuck radio.

Removing the forced transmit removes transmissions that were, by definition, sent into a channel known to be occupied. Collisions fell accordingly. This is the mechanism working as described.

The airtime rise is the cost and needs saying plainly: deferring rather than forcing means packets are transmitted later, and a run of fixed length ends with more of them still in flight and retried. Reach fell by nearly four points for the same reason.

So the trade is spectrum efficiency against latency. On a band where airtime is scarce, fewer collisions for slightly slower delivery is usually the right side of that trade, but it is a trade rather than a free improvement.

Should it be adopted?

Yes, with a caveat about the original intent

Adopt, but keep the diagnostic. The forced transmit exists to break a deadlock with a wedged radio, and that is a real failure mode on real hardware. The right change is the one measured here plus a bound: back off, and force only after several consecutive timeouts rather than the first, so a genuinely stuck radio still recovers while a busy channel is respected.

For

  • Fewer collisions, measured, on the network where the condition actually occurs.
  • Fewer transmissions for nearly the same delivery.
  • No runtime cost and no new state.
  • Keeps the error flag, so the stuck-radio case remains diagnosable.

Against

  • Reach fell 3.9 points and airtime rose 13.9% over a fixed-length run.
  • It removes the recovery path for a radio whose interrupt flags are genuinely stuck, which is the case the original code was written for.
  • The effect depends on congestion, so a quiet network sees nothing.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
