The negative control that failed, and what it exposed

A repeater's loop detection counts how many times its own hash appears in a packet's path, so a cycle that does not pass through the node checking is invisible to it. Rejecting any repeated hash was pre-registered as a negative control that should change nothing. It cost eighteen points of reach, and the reason is a one byte hash.

Where it comes from

MyMesh::isLooped() walks the path counting matches against self_id, and rejects when the count reaches a threshold indexed by path hash size. At a three byte hash all three loop-detection settings are 1 and therefore identical by construction, which is a separate finding from an earlier study.

The gap is that a packet going round a cycle A to B to C to A is only detected by A. B and C forward it happily.

The change

After the existing check, also reject a packet whose path contains any hash twice, whoever it belongs to.

for (int i = 0; i < count; i++) {
  for (int j = i + 1; j < count; j++) {
    if (memcmp(&path[i * hash_size], &path[j * hash_size], hash_size) == 0) {
      return false;   // a cycle, even if we are not in it
    }
  }
}

Cost. O(n squared) over at most 63 entries, on a path that is usually under five.

What was predicted, before running it

Little or no effect. An earlier study found 0 of 8,270 observed paths contained a repeated hash. The arm was included specifically so that a change in the numbers would tell us the harness was generating loops the real network does not have.

What happened

The control failed, and the firmware is the reason

Reach fell from 56.2% to 38.0%, eighteen points, with transmissions down 13.8% and receptions down 18%. A negative control that moves this much normally means the harness is wrong. This time the harness is fine and the idea is unsafe.

Why it came out that way

getPathHashSize() is (path_len >> 6) + 1, so every path shorter than 64 hops uses a one byte hash. On this network 311 nodes share 256 possible values, and two different nodes having the same hash byte is not an edge case, it is the normal state of affairs.

The rule 'reject any repeated hash' therefore rejects legitimate paths whenever two distinct nodes along the path happen to collide. The chart above is the birthday calculation: a four hop path is rejected 2.3% of the time, a twelve hop path 23% of the time, a twenty hop path more than half the time.

That is exactly the shape of the measurement. Transmissions fell moderately, 13.8%, because short paths near the origin mostly survive. Reach collapsed by eighteen points because the deep paths, the ones that carry a flood to the far side of the network, are precisely the ones the rule kills. The far hops are where reach lives.

So the negative control did its job, just not in the way it was designed to. It was there to catch a harness generating fictitious loops. Instead it caught a real property of the protocol: path hashes are too short to support any rule of the form 'this hash appeared twice' beyond the one the firmware already has, which compares against the node's own identity and is therefore immune to collisions with other nodes.

This is worth knowing beyond this idea. Any future proposal that reasons about identity from a path hash inherits the same defect at any path length under 64 hops.

Should it be adopted?

No, and the reason generalises

No. The rule is unsound at the hash width the protocol actually uses, and no amount of tuning fixes that. If cycle detection beyond a node's own identity is wanted, it needs a wider hash, which costs airtime on every packet, and the case for that would have to be made from evidence that cycles happen at all. The available evidence says they do not: zero repeats in 8,270 observed real paths.

For

  • It does detect cycles that the current check cannot see, which was the stated gap.
  • Cheap to compute on realistic path lengths.
  • As an experiment it produced the most useful finding in the series: it put a number on how unreliable a one byte path hash is as an identity.

Against

  • Eighteen points of reach on a real topology.
  • The false positive rate is a property of the hash width, not of the implementation, so it cannot be tuned away.
  • It gets worse as paths get longer, which means it degrades exactly where a mesh needs to work hardest.
  • The problem it solves has never been observed in real traffic.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
