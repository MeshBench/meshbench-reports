A second chance for an acknowledgement

An acknowledgement crossing a marginal link gets one attempt, and losing it costs a whole repeated exchange rather than one packet. Sending a second one below a signal-to-noise threshold is cheap. This series could not measure it, because nothing in it sends a request.

Where it comes from

Mesh::getExtraAckTransmitCount() returns 0. The repeater overrides it with _prefs.multi_acks, an operator setting applied to every acknowledgement regardless of how good the link is.

So the missing behaviour is not redundancy itself, which exists, but any awareness of whether this particular path needs it.

The change

logRxRaw() already receives the signal-to-noise ratio of every packet the node hears. Remembering the most recent one costs a float. Below -5 dB, send one more acknowledgement than the operator asked for.

uint8_t getExtraAckTransmitCount() const override {
  if (study_last_snr < STUDY_POOR_SNR) return _prefs.multi_acks + 1;
  return _prefs.multi_acks;
}

Cost. One extra transmission per exchange on a marginal path, and a float of state.

What was predicted, before running it

Round trip completion improves on marginal paths for a small, bounded airtime cost. Pre-registered as the most likely of the eight to be a straightforward win.

What happened

Not exercised by this workload

Identical to three other arms in this series. Every run floods one message outward and measures where it reaches; no node sends a request, so no acknowledgement is ever generated and the modified code never executes.

Why it came out that way

This is a measurement gap rather than a result. The study harness originates floods and counts deliveries. Acknowledgements belong to request and response traffic, which it does not produce.

The arm did run its own binary, confirmed by checksum on every run record, and it returned the control's behaviour in every respect that this workload can see.

The pre-registration was also wrong about the code, which is worth recording. It stated that the repeater does not override getExtraAckTransmitCount(). It does, through _prefs.multi_acks. The idea as written would have added a second mechanism beside an existing one; what was implemented instead makes the existing one aware of link quality.

Measuring it requires a scenario with request and response exchanges over paths of known quality, and a completion-ratio metric. Neither exists yet.

Should it be adopted?

Promising, unmeasured

Worth adopting on reasoning, and worth measuring before it is. The asymmetry is real: one extra transmission against a timeout plus a repeated exchange is a good trade whenever the loss probability is appreciable. The threshold is the part that needs evidence, because -5 dB is a guess and the right value depends on the modulation in use.

For

  • The information it needs is already delivered to the firmware on every received packet.
  • Bounded cost: one extra transmission, only on links below the threshold.
  • Builds on the existing operator setting rather than adding a second knob.
  • Failure mode is mild: at worst it spends a little airtime on a link that did not need help.

Against

  • Entirely unmeasured here.
  • The threshold is arbitrary and modulation dependent.
  • SNR of the last packet heard is a proxy for the quality of the return path, which is not the same link; reachability is asymmetric.
  • On a congested network, extra transmissions are the thing least wanted.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
