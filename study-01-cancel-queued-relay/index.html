Cancelling a relay somebody else already sent

A repeater holding a flood packet to retransmit has no way to change its mind, however many neighbours it hears send the same packet first. Adding one saves twelve per cent of the transmissions on a three hundred node mesh. It also costs nine points of reach, and that is the part worth reading.

Where it comes from

Dispatcher::calcRxDelay() gives a better-scoring node a shorter delay, so the best-placed relay transmits first. That is a deliberate design and nothing acts on its outcome.

_tables->markSeen() stops a second copy of a packet being queued, which is a different thing: it prevents duplication at the moment of receipt. There is no cancellation path anywhere in Mesh.cpp, Dispatcher.cpp or the repeater. removeOutboundByIdx() exists on the packet manager and is never called for this purpose.

So a node that has queued its retransmit still transmits it when its timer expires, however many neighbours have already sent the identical packet in the meantime.

The change

A small ring of pending flood hashes on the dispatcher. When a flood arrives whose hash matches one already queued outbound, mark that entry heard. When the queued copy comes up for transmission, drop it instead of sending it.

bool Dispatcher::takePendingFloodHeard(const uint8_t* hash) {
  int i = findPendingFlood(hash);
  if (i < 0) return false;
  bool heard = pending_flood_heard[i];
  pending_flood_used[i] = false;   // done with it either way
  return heard;
}

Cost. One hash comparison per received flood packet against a queue of at most a few entries, plus MAX_PENDING_FLOOD hashes of RAM.

What was predicted, before running it

Transmissions and duplicate receptions fall substantially, with delivery unchanged. This was pre-registered as the single largest airtime saving available in the eight.

What happened

Cheaper, and it delivers less

Transmissions fell 11.9% and collisions 11.3%, but reach fell from 56.2% to 47.5%, which is nearly nine points. The saving is real and so is the cost, and on this network the cost is larger than the saving.

Why it came out that way

The transmissions it removes are the ones a human would call redundant, and the numbers agree: eleven per cent fewer transmissions produced eleven per cent fewer collisions. That part of the hypothesis held exactly.

The reach loss is the part the hypothesis did not anticipate, and it follows from what the node actually knows. Hearing a neighbour relay a packet is evidence that the packet is travelling. It is not evidence that it reached everybody this node could have reached. On a mesh with asymmetric links, and this one is built from real positions and real antennas, node C often hears node B while some node D hears only C. Cancelling C's relay silently removes D.

This also explains why the same change measured exactly nothing on the 58 node Fife network: identical transmissions, identical receptions, the control's numbers digit for digit. With rx_delay_base at its shipped 0.0 every node relays on receipt, so on a small network nothing sits in the queue long enough to be cancelled. On a 311 node network the queue is full because the channel is contended, and the mechanism has plenty to act on. The same patch is inert or harmful depending on the size of the network it runs on, which is an argument for testing protocol changes on a real topology rather than a lattice.

Should it be adopted?

Not on its own

Not as it stands. Nine points of reach is too much to pay for twelve per cent of the airtime, and a repeater's job is delivery. It is worth revisiting with a condition attached, for example only cancelling when the node that relayed first is one this node can hear and has a better score, which is information the firmware already has from calcRxDelay().

For

  • Eleven per cent fewer transmissions and eleven per cent fewer collisions, measured, on a real 311 node topology.
  • Very cheap: one hash comparison per received flood, and a handful of bytes of RAM.
  • The mechanism is sound and the effect is in the direction claimed. It removes transmissions that carry no new information to anybody who was listening to the node that went first.
  • It composes with the receive delay: on an earlier 58 node run the pair together removed 22.7% of transmissions where the delay alone removed 15.2%.

Against

  • Nine points of reach on this network, which is the metric a repeater exists to serve.
  • The decision is made on incomplete information. A node cannot tell from hearing a relay whether that relay covered its own neighbours.
  • The effect depends on network size in a way that makes it hard to reason about: inert on a small mesh, harmful on a large one.
  • It interacts with rx_delay_base, so its behaviour changes if that default is ever restored.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
