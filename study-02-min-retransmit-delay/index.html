A retransmit delay that cannot be zero

Two repeaters hearing the same flood can both draw a delay of zero and transmit on the same millisecond. Forbidding zero is a one token change. It made the network transmit seven per cent more and spend a fifth more airtime, which is the opposite of the intended direction and entirely explicable.

Where it comes from

MyMesh::getRetransmitDelay() scales an airtime estimate by tx_delay_factor and then draws uniformly from zero to five times it:

return getRNG()->nextInt(0, 5*t + 1);

The lower bound is zero, so two nodes can both choose to transmit immediately.

The change

Change the lower bound to one, so every relay waits at least one tick.

uint32_t MyMesh::getRetransmitDelay(const mesh::Packet *packet) {
  uint32_t t = (_radio->getEstAirtimeFor(...) * _prefs.tx_delay_factor);
  return getRNG()->nextInt(1, 5*t + 1);   // was nextInt(0, ...)
}

Cost. None.

What was predicted, before running it

A small reduction in collisions. Pre-registered explicitly as a sanity arm: a one token change with a mechanically obvious effect, included so that a large delta in either direction would tell us the harness deserved suspicion.

What happened

More traffic, slightly more reach

Transmissions rose 7.2%, airtime rose 19.4% and collisions rose 9.5%, while reach rose 2.5 points. Not the direction predicted, and large enough to need an explanation rather than a shrug.

Why it came out that way

The prediction was wrong about the sign because it treated a simultaneous transmission as pure waste. It is not. When two neighbours transmit the same flood on the same millisecond, one of two things happens: they collide and both are lost, or capture effect delivers the stronger one and the weaker is discarded by the receiver as a packet it has already seen. In the second case the network has spent one node's airtime and gained a delivery.

Separating them in time converts those coincidences into two separate, successful, individually audible transmissions. Every one of them is then heard, deduplicated by markSeen() at the receivers, and counted, which is exactly the nineteen per cent of extra airtime with almost no extra receptions to show for it: receptions moved 0.1%.

The 2.5 points of reach is the honest upside and it is small. Spreading relays does reduce the cases where two genuinely useful transmissions destroy each other. It is not worth a fifth of the network's airtime.

As a sanity arm this did its job in a way that is worth stating plainly: the delta is large enough that it would be reasonable to suspect the harness. It is not the harness. The control reproduced identically in this sweep and in six others, and the mechanism above explains the sign without needing the measurement to be wrong.

Should it be adopted?

No

No. It costs nineteen per cent more airtime for two and a half points of reach, on a band where airtime is the scarce resource and where the shipped duty cycle default is already far above what the regulations allow. If the goal is fewer wasted simultaneous transmissions, the receive delay in idea 9 achieves it in the opposite direction: fifteen per cent less airtime with delivery unchanged.

For

  • Two and a half points of reach, measured.
  • A single token of change, no state, no memory, no runtime cost.
  • It removes a genuine degenerate case: two nodes choosing the same instant.

Against

  • Nineteen per cent more airtime and seven per cent more transmissions.
  • Nine and a half per cent more collisions, which is the opposite of the intent.
  • Receptions did not move at all, so the extra transmissions bought almost nothing.
  • It makes the duty cycle problem worse on a network that already has one.

How it was run

The 311 node Scotland and Ireland import, built from live CoreScope with the transport regions the real nodes hold. Both arms run in the same sweep, on the same two seeds, against the same network, with only the repeater firmware differing. Four senders, spread rather than adjacent, so they contend with the mesh rather than with each other. Ninety seconds of simulated time per run.

Node storage is wiped before the sweep. A node keeps its preferences between runs exactly as hardware does, so one that has run before loads its stored value and never reaches a changed default: both arms then return identical numbers and the change looks inert.

The control is MeshCore at the commit repeater-v1.17.0 points at, built by the same script as the arm. It produced 573 transmissions and 4,830 receptions in every sweep of this series, seven sweeps over three hours. That is the reproducibility check, and without it none of the deltas on this page would be attributable to the firmware.

Limits

Two seeds. The plus or minus twenty per cent figure quoted elsewhere for this simulator belongs to a different measurement, reach under contention from around eight simultaneous senders; it is a property of that contention rather than of the simulator, and it is not quoted here as though it were universal. What can be said is that the control repeated exactly, so a difference between arms is the firmware. Two seeds is still a thin basis for a small delta, and anything under a few per cent on this page should be read as unproven rather than as a result.

The simulator is kinder than the air: no multipath, no body loss, no oscillator error, no interference beyond the mesh's own traffic. Every one of those omissions makes real links worse, so the absolute numbers are a best case and the comparison is the finding.

The MeshCore branch carrying this change is local and is not pushed anywhere.
